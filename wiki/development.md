# Development and checks

The code contains in-memory metadata modules, a Windows directory scanner and a desktop consumer. Most tests use synthetic metadata; Windows engine tests also create and remove small temporary fixtures and query drive metadata. They do not scan whole volumes.

## Requirements

Use Rust 1.94.1 with rustfmt and clippy. Windows 11 x64 is the intended product platform, and the Windows CI job also exercises preservation of native file names that are not valid Unicode.

The in-memory modules use only std; the Windows engine uses windows-sys 0.61.2. The default `desktop` feature adds optional egui/eframe 0.35.0 with glow, default fonts, AccessKit and window persistence for the binary. A reduced development profile keeps builds smaller by limiting debug information, disabling incremental caches and turning off dependency debug information; release builds are compiled separately.

## Run the checks

From the source repository root:

```text
cargo fmt -- --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo test --locked --no-default-features
cargo build --locked
```

Configure build/cache/temporary locations in your own shell session when needed. Do not change machine-wide settings or fill a disk to reproduce a test. Fixtures should be small and synthetic; a million-entry memory benchmark is not a reason to create a million real files.

[GitHub Actions](https://github.com/Yivas/hogmap/actions) runs the checks on Windows. CI also fails if `allow(unsafe_code)` appears outside the audited `src/scan_win.rs`, `src/volume.rs` and `src/name_arena.rs` boundaries. A successful test job is not evidence of faithful native-window behavior, whole-volume accuracy or a portable ZIP.

## Run the window

Run `cargo run --locked` from the repository root on Windows. The window opens a chooser and does not automatically scan a disk. Select a real listed drive or enter an existing directory such as `C:\` or `C:\scan-fixture`, then choose Start. Drive listing runs in a background task with “Listing drives…” shown meanwhile. Reopening uses the session cache; Refresh drives explicitly updates it. Path and volume checks run off the UI thread before the scanner starts; the header's label and free/total bytes come from a fresh drive query, not the chooser's cached list, so the first Start and a later rescan show current capacity. Invalid or non-directory paths are rejected, as are observed reparse points/junctions and reparse ancestors. The engine reads directory metadata, never file contents, and does not modify the selected tree. Begin with a small local fixture. Selecting a mapped drive or network path can cause Windows filesystem I/O to a server.

File → Explore synthetic sample instead streams generated metadata in memory; its header explicitly says sample and has no volume capacity. Ctrl+N opens the chooser again. Rescan or F5 repeats the selected scan root or sample, not the zoomed folder, and clears navigation and selection. Stop scan or Escape outside the highlight field requests cancellation immediately while the consumer keeps draining queued events. Escape or the chooser's Close while a path is being checked cancels that preparation. An in-flight synchronous Windows call has no cancellation deadline. Replacement and close show “Stopping…” while polling for completion, without joining unfinished threads on the UI thread. A close with work still running waits up to two seconds for it to finish; if a thread is still blocked after that, the window closes and detaches it instead of blocking shutdown. Repeated requests coalesce; a replacement waits for the old producer to return instead of accumulating threads.

Real window scans use the observed backend. After Finished, conflicting hardlink identities are checked on a cancellable metadata worker, with budgeted preparation/application on the UI thread. The existing status reports progress, corrected charges and unresolved reasons. Stop/Escape also cancels these checks; rescan/close retire the worker without joining blocked I/O. Stale generations are discarded and the large index is not cloned or moved to the worker.

The leading status reports producer activity separately from metadata completeness. A finished scan can still have incomplete metadata; the sample deliberately includes unknown sizes and inaccessible directories. Failures show readable safety/resource messages; other Windows error codes appear as `error N`, or `code N` once for a drive-listing failure. The full status detail is available on hover and in the status area's accessible label: protocol diagnostics, the latest directory failure and, once the engine returns, fallback directories, reparse/cloud skips, invalid names, pending-memory limit hits, maximum queue/local-frontier depth and cancellation wakeups. Ordinary directory failures stay in that detail, not as a permanent red fatal-error message.

Click to select, double-click a folder or small-item aggregate to open it, and use Back/Forward/Up/Home to navigate. Backspace goes up, Alt+Left/Right moves through history and Escape leaves the highlight field without cancelling. View → Logical size and View → Allocated size choose what the map weighs; logical is the default and the choice is not remembered after closing. Switching redraws the map and its labels together and keeps the current folder, opened members and a selected file or folder; a selected small-item group stays selected only if the same items are still grouped. After a switch, an opened group is captioned “N grouped items”, because its members may no longer be the small ones. View → Dark and View → Light switch the theme straight away, and the choice is remembered for the next start. The status line shows the dataset root and the path to the current folder, plus the small-item count when the map is open inside an aggregate. The highlight field accepts [name and logical-size filters](./filters.md); it dims non-matches without changing map area or totals, and invalid input keeps the previous valid highlight. The match counter appears only while the field has non-whitespace text.

### Map legend

The window opens in the dark theme, or in the theme chosen last time. A saved light theme is applied before the first frame, so it does not flash dark. Both themes draw the same rectangles, headers and labels; only colors differ. Some states also have a mark that does not depend on color; the others are told apart by fill only.

- Brown (dark theme) or tan (light theme): directories, with a name/size header when space permits. Header bands get slightly lighter (dark) or darker (light) with each nesting level, up to four levels. Directory borders are drawn darker than the thin seams between files.
- Blue: files with known bytes in the selected metric (logical by default, or allocated).
- Neutral labelled Free space and Reserved by Windows cells: independently known final volume measurements, only in a finished unzoomed whole-volume Allocated view. They support keyboard focus and accessible metadata names, not file selection, zoom or actions. Logical, folder and zoomed views omit them.
- Lilac: small-item aggregates, with a dotted inner border when the cell is at least 24 px on each side. Each has a count/size label when it fits and a hover tooltip such as “12 small items · 1.2 MiB”; double-click opens those members. The tooltip names the metric, such as “12 small items · Apparent size: 1.2 MiB logical”. Inside that member view the root header keeps the parent folder's name and adds the subset, such as “photos · 12 small items - 1.2 MiB”.
- Gray with a dashed inner border: partial entries, such as a folder whose scan was cancelled before it finished.
- A dotted line under a header: the folder's total is incomplete, because some sizes are unknown or some content below it is partial or could not be read. Its size reads “+ unknown”. Unknown sizes are not zero and have no area of their own.
- Dimmed, near-background gray: non-matching entries while highlighting; olive (dark) or muted beige (light): an unknown filter decision.
- A thin outline follows the pointer and a thicker, stronger outline marks the selection; on cells smaller than 8 px both are drawn just outside the cell. Keyboard focus is a dashed ring with a solid backing, outside the cell.

Marks are skipped on cells smaller than 8 px on either side.

Map labels are chosen to keep a contrast ratio of at least 4.5:1 against their fill in both themes. That checks the palette, not full accessibility.

The total is labelled Apparent size: `known_bytes + resolution_delta_bytes` for the selected metric. The charged record uses the authoritative size; aliases retain listed sizes. There is no full per-name authoritative correction or error bound. Apparent size can exceed disk capacity; unique bytes per identity remain secondary status/tooltip detail. Cell sizes and areas use the same per-name apparent total: logical by default, or observed allocated bytes in the allocated view (`Index::summary_for`, `layout_with_metric`, `layout_members_with_metric`), with its own unknown sizes, missing identities and conflicts. Neither is physical or recoverable space, and highlight size conditions stay logical in both views. The header displays queried global filesystem free/total capacity separately, or unknown if unavailable. Capacity uses the Actual fields of GetDiskSpaceInformationW (available from Windows 10 build 17763), never its caller-quota fields. The existing chooser/header hover and accessible details show the provider, query age and a reason when capacity is unknown; exact capture time and provenance are retained in memory, not saved. A local non-elevated Windows 11 metadata test exercises the real provider; quota-enabled/pool environments and atomic reconciliation with a scan are not verified. See the [capacity semantics](https://github.com/Yivas/hogmap/blob/main/docs/core.md#windows-metadata-engine). The tree and known final free/reserve share one byte scale, normalized only over displayed bytes. The status says the map is not a complete disk partition and reports estimated difference against allocated apparent total at both endpoints, or why it is unavailable. D <= 0 stays a signed discrepancy, not area; arithmetic overflow is reported. Difference has neither a cell nor an implicit blank area. Unknown components are omitted; reserve failure need not erase known free. Not-yet-scanned/inaccessible-space blocks, snapshots, export and alternate view modes are not implemented. Headless geometry and accessibility checks are not native visual acceptance.

Only the window geometry and the chosen theme are saved in eframe's application-data directory. Names, paths, filter text and navigation are not saved, and egui's own widget and window memory is not saved either. A stored theme value that is missing, unknown or unreadable falls back to dark. AccessKit is enabled, but a full screen-reader and DPI acceptance pass is still pending. If eframe returns a startup error, HogMap prints it to stderr and exits with code 1; there is no native message box or automatic graphics-backend fallback.

## Know the boundaries

- `src/index.rs` owns the flat metadata snapshot, entry IDs and per-metric listed/identity-accounting facts and the checked `MetricSummary::apparent_bytes()` area total. `known + delta = unique + shared` remains true; unique/shared are secondary facts, not geometry weights.
- `src/filter.rs` parses and evaluates name/logical-size conditions.
- `src/composition.rs` evaluates typed accounting eligibility without GUI dependencies. Known final free/reserve availability is independent of positive D. Fixed-answer tests cover apparent totals with resolved charges and listed aliases, hard gates, signed discrepancies, overflow, zero and unknowns; unreadable/unknown/skipped/fallback coverage remains diagnostic, without a residual-block drawing policy. Headless UI tests cover proportional cells, both themes, visibility, keyboard/AccessKit behavior, cancellation and stale generations.
- `src/scan.rs` defines the generation-tagged scanner contract, bounded batches and the reducer that builds an index.
- `src/scan_win.rs` enumerates Windows directory metadata with bounded workers. The additive `run_win_scan_observed_with_options` returns outcome/report plus a generation-linked origin sidecar: scope, namespace observations and bound capacity endpoints, with typed unknowns/cancellation. Its origin queries use metadata-only directory handles; scheduling retains the legacy seek-penalty hint, worker policy and conditional NTFS MFT ordering. Queries run outside the shared observation mutex, with a reusable buffer per observed worker. It compares directory serial64 first and attempts GUID paths only on mismatch/unavailable identity; separate counters retain both kinds of evidence. Serial64 agreement is not GUID proof. Post-enumeration metadata queries run before the terminal and can delay it, including on a blocked network query; legacy mode is unaffected. Legacy scanner signatures and their Copy counts/timings-only report are unchanged and make no supplementary observation calls; the UI uses the observed path, retaining facts in RAM only. The root's filesystem name is captured in the same existing by-handle call as its support flags, without an extra query/open. The [origin contract](https://github.com/Yivas/hogmap/blob/main/docs/core.md#optional-origin-observations) explains opaque identities, alias ambiguity, lifetime and non-atomic endpoints; this is not reconciliation or gray eligibility. At that boundary an unsupported all-zero 128-bit file ID becomes unknown identity, not a shared hardlink; known logical/allocated sizes, including zero, are preserved and charged individually. Missing-identity counts are per metric and independent of size/state coverage. The primary path can lack identity while allocated size stays known; the fallback lacks both. `src/volume.rs` queries drive roots, labels, capacities, filesystem and whether the device reports a seek penalty. The scanner currently uses four workers on both SSD and HDD (the HDD value is provisional), and on NTFS hard disks it visits pending folders in MFT record order to reduce head movement. `examples/scan_bench.rs` measures a scan from the command line without printing paths or names; see CONTRIBUTING.
- `src/synthetic.rs` streams a separate deterministic in-memory tree through that contract.
- `src/treemap.rs` computes squarified rectangles, headers and navigable aggregates without drawing, weighted by logical or allocated bytes.
- `src/main.rs` and `src/ui/` own the desktop consumer, cached rendering, navigation and UI strings.
- `tests/core.rs`, `tests/scan.rs`, `tests/treemap.rs`, `tests/aggregate_navigation.rs` and `tests/navigation.rs` check public behavior and pure UI logic with fixed expected answers, including independent logical/allocated charges, conflicts, missing identities and per-metric overflow. Unit tests in `src/ui/` check location text, volume-choice mapping, path validation, scan-code messages, theme contrast and the stored theme preference. `tests/scan_win.rs` exercises small real Windows fixtures, not whole drives. A module-local aligned-buffer fixture feeds the actual Windows parser and index with equal-size zero-ID files, including known-zero sizes, and nonzero 128-bit hardlink IDs; this is simulated unsupported-provider metadata, not runtime reproduction on an installed filesystem. One native module-local regression constructs four small owned files (normal, compressed, sparse and an empty default stream with named-stream data), closes construction handles, then exercises the actual scanner/events/reducer/index path. It compares indexed allocation with the raw field from a separate native directory enumeration, independent of the scanner parser and reducer; this checks value transport, not physical attribution. It prints anonymous allocation observations, explicit capability omissions and cleanup confirmation; `allocation_verification_complete=1` follows those fidelity assertions and means all requested modes and primary enumeration ran with known allocation. A passing test with omissions does not certify those modes. The [local observations and stream limits](https://github.com/Yivas/hogmap/blob/main/docs/core.md#windows-metadata-engine) do not establish all-stream or physical totals.
- The [core contract](https://github.com/Yivas/hogmap/blob/main/docs/core.md) is the technical reference for implemented behavior.

For an owned synthetic tree of 20021 empty directories, five alternating warm runs per mode gave median observed overhead of 75.722% originally, 35.369% with per-directory GUID queries outside the mutex, and 0.203% with serial64-first queries. The preselected small-cost threshold was 5%, so serial64-first was retained. This is a local comparison with variable samples, not a general performance or UI promise; [timings, spread and evidence limits](https://github.com/Yivas/hogmap/blob/main/docs/core.md#observed-scan-cost) are recorded together. The headless example defaults to legacy; process-local `HOGMAP_BENCH_OBSERVED=1` selects observed scans and anonymous counters without changing benchmark guards. Observed diagnostics also include root scope/issues, capacity endpoints, relative wall-clock times, identity/path continuity and signed differences against allocated unique bytes, with explicit unknown reasons. They do not calculate eligibility or decide the treatment of unreadable directories; real-volume capacity and difference values are not published here.

Checked u32 entry-ID and name-arena ceilings return `CapacityExceeded`; these [representation limits](https://github.com/Yivas/hogmap/blob/main/docs/core.md#metadata-index) are not a safe process-memory budget, and allocation exhaustion can occur sooner.

Entry IDs belong to one index snapshot. The scanner contract checks the owning generation before applying records; the reducer never resolves an unknown parent later. IPC, privileged NTFS reading and physical attribution are not implemented. Small owned Windows fixtures now check the public scanner against an independent FindFirstFileExW walk for names, counts and logical sizes, and exercise create/delete changes with a publication gate. A discovered directory removed before opening keeps its real Win32 failure code and incomplete coverage; concurrent entries are not an atomic snapshot. A real path and a scan root longer than 260 UTF-16 units are enumerated from both ordinary and extended-prefix root arguments, using extended paths internally. These checks do not establish UNC or alternate registry/manifest configurations, desktop chooser acceptance, real cloud-provider behavior or safety against adversarial path replacement; see the [engine limits](https://github.com/Yivas/hogmap/blob/main/docs/core.md#windows-metadata-engine). Layout rebuilds are limited to four per second while scanning and cached otherwise; hover and theme changes do not rebuild the tree, and a metric switch rebuilds it at once.

## Propose a change

Read [CONTRIBUTING](https://github.com/Yivas/hogmap/blob/main/CONTRIBUTING.md) and open an issue to agree the scope before writing a pull request. Small documentation corrections need no prior issue.

A useful core bug report identifies the commit, Rust version and a synthetic reproduction. Do not include personal paths, machine names, credentials, disk listings or screenshots containing file names. Undisclosed vulnerabilities belong in the [private security channel](https://github.com/Yivas/hogmap/security/advisories/new), not in a public issue.
