# Development and checks

The code contains in-memory metadata modules, a Windows directory scanner and a desktop consumer. Most tests use synthetic metadata; Windows engine tests also create and remove small temporary fixtures and query drive metadata. They do not scan whole volumes.

## Requirements

Use Rust 1.94.1 with rustfmt and clippy. Windows 11 x64 is the intended product platform, and the Windows CI job also exercises preservation of native file names that are not valid Unicode.

The in-memory modules use only std; the Windows engine uses windows-sys 0.61.2. The default `desktop` feature adds optional egui/eframe 0.35.0 with glow, default fonts, AccessKit and window persistence for the binary. A reduced development profile keeps builds smaller by limiting debug information, disabling incremental caches and turning off dependency debug information; release builds are compiled separately.

## Run the checks

From the source repository root:

```text
cargo fmt -- --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo test --locked --no-default-features
cargo build --locked
```

Configure build/cache/temporary locations in your own shell session when needed. Do not change machine-wide settings or fill a disk to reproduce a test. Fixtures should be small and synthetic; a million-entry memory benchmark is not a reason to create a million real files.

[GitHub Actions](https://github.com/Yivas/hogmap/actions) runs the checks on Windows. CI also fails if `allow(unsafe_code)` appears outside the audited `src/scan_win.rs`, `src/volume.rs`, `src/name_arena.rs`, `src/ui/shell_menu.rs`, `src/ui/file_dialog.rs` and `src/watch.rs` boundaries. A successful test job is not evidence of faithful native-window behavior, whole-volume accuracy or a portable ZIP.

## Run the window

Run `cargo run --locked` from the repository root on Windows. The window opens a chooser and does not automatically scan a disk. Select a real listed drive or enter an existing directory such as `C:\` or `C:\scan-fixture`, then choose Start. Drives appear as compact aligned rows with separate Free and Total columns; longer lists scroll instead of leaving a partly hidden tile row. Unknown capacity is written as unknown, and known zero stays 0 B. A neutral used/free bar appears only with valid known capacities. Click a row to fill Path, or focus it and press Enter to start. Drive listing runs in a background task with “Listing drives…” shown meanwhile. Reopening uses the session cache; Refresh drives explicitly updates it. Path and volume checks run off the UI thread before the scanner starts; the header's label and free/total bytes come from a fresh drive query, not the chooser's cached list, so the first Start and a later rescan show current capacity. Invalid or non-directory paths are rejected, as are observed reparse points/junctions and reparse ancestors. The engine reads directory metadata, never file contents, and does not modify the selected tree. Begin with a small local fixture. Selecting a mapped drive or network path can cause Windows filesystem I/O to a server.

File → Explore synthetic sample instead streams generated metadata in memory; its header explicitly says sample and has no volume capacity. The toolbar visibly names New scan, Rescan and Stop beside their icons, with shortcut tooltips. Scan actions, Back/Forward/Up/Home and highlight are separated by task. Snapshot and text actions live in File, not the toolbar; the nested/flat choice, Group by, ghosts and Options live in View, and none of them has a toolbar button. There is no Snapshots tab. Disabled controls only represent real actions temporarily unavailable. Ctrl+N opens the chooser again. Rescan or F5 repeats the selected scan root or sample, not the zoomed folder, and clears navigation and selection. Stop scan or Escape outside the expression field requests cancellation immediately while the consumer keeps draining queued events. Escape or the chooser's Close while a path is being checked cancels that preparation. An in-flight synchronous Windows call has no cancellation deadline. Replacement and close show “Stopping…” while polling for completion, without joining unfinished threads on the UI thread. A close with work still running waits up to two seconds for it to finish; if a thread is still blocked after that, the window closes and detaches it instead of blocking shutdown. Repeated requests coalesce; a replacement waits for the old producer to return instead of accumulating threads.

Real window scans use the observed backend. After Finished, conflicting hardlink identities are checked on a cancellable metadata worker, with budgeted preparation/application on the UI thread. The existing status reports progress, corrected charges and unresolved reasons. Stop/Escape also cancels these checks; rescan/close retire the worker without joining blocked I/O. Stale generations are discarded and the large index is not cloned or moved to the worker.

The leading status reports producer activity, entry count, apparent size and metadata completeness without appending the long accounting explanation. The status occupies one 24-point line and includes elapsed time; its hover/accessible detail keeps “Apparent size · counted per name · not recoverable space”. Ordinary progress is coalesced to about 4 Hz, with immediate errors, terminal states and explicit interactions. A finished scan can still have incomplete metadata; the sample deliberately includes unknown sizes and inaccessible directories. Failures show readable safety/resource messages; other Windows error codes appear as `error N`, or `code N` once for a drive-listing failure. The full status detail is available on hover and in the status area's accessible label: protocol diagnostics, the latest directory failure and, once the engine returns, fallback directories, reparse/cloud skips, invalid names, pending-memory limit hits, maximum queue/local-frontier depth and cancellation wakeups. Ordinary directory failures stay in that detail, not as a permanent red fatal-error message.

Click to select, double-click a folder or small-item aggregate to open it, and use Back/Forward/Up/Home to navigate. Backspace goes up, Alt+Left/Right moves through history and Escape leaves the expression field without cancelling. View → Logical size and View → Allocated size choose what the map weighs; logical is the default and the choice is not remembered after closing. Switching redraws the map and its labels together and keeps the current folder, opened members and a selected file or folder; a selected small-item group stays selected only if the same items are still grouped. After a switch, an opened group is captioned “N grouped items”, because its members may no longer be the small ones. View → Dark and View → Light switch the theme straight away, and the choice is remembered for the next start. Without a selection, the location stays in hover/accessible text rather than an isolated fallback caption. Clicking a cell shows a brief selected name and apparent size; its full path remains accessible. Folders and groups also say “Double-click to open”. More/Less detail is available in the toolbar and View, with Ctrl++/Ctrl+= and Ctrl+-. It changes the number of levels drawn below the current folder (1–64, default three), which is relative to the zoom, so opening a folder shows that folder's own levels. The minimum cell area is a separate control in View → Options…, and neither choice is saved. Free and Not yet scanned have their own switches in the toolbar and View, repeated with the same state; hiding one removes its cell and gives the space back to the tree without changing any figure or classification. Long paths keep their full tooltip and accessible text. The expression field accepts [name/folder masks, logical/allocated sizes, ages, attributes, classes and tags](./filters.md). Highlight dims non-matches without changing geometry. Filter removes non-matches, retains undecided files and reports matched/undecided/full snapshot bytes separately; it omits volume/residual cells. Use the mode selector or Ctrl+Shift+F; neither mode nor expression is saved. Invalid input keeps the previous valid filter. The match counter appears only with non-whitespace text. View lists Ctrl+1/2/3/4 to assign Red/Yellow/Green/Blue tags to the selection and Ctrl+0 to clear it. Numbered marks, tooltips and accessible names include inherited tags. View → File classes… edits session definitions and reparses the active filter on every applied change; see [Filters](./filters.md#file-classes) for validation, deletion confirmation and the missing-class warning.

### Progress, watching, notices and bookmarks

While a scan runs, an indeterminate 2-point bar is drawn along the bottom edge of the status line, so progress never resizes the map. It reports activity, not a fraction: the tooltip gives accepted entries, completed and failed immediate directory outcomes and the current root's known bytes for the selected metric, and says that the total entry count is unknown. No volume percentage is invented. A one-pixel coverage strip on the map's left edge adds one column per visible depth band, divided by entry count into complete, partial/stale/inaccessible and pending/unknown entries, with those counts on hover. The counts describe drawn cells and grouped members, not bytes, and a complete directory means its immediate children were enumerated, not that its descendants are complete.

View → Watch for changes follows one local root for the session and starts only after the scan has finished, because notifications against an index that is still being built would describe incomplete data. It holds one metadata-only directory handle and reads recursive name, attribute and size notifications; no notification path is opened or followed, and reparse, offline, recall, UNC, device and mapped remote roots are rejected before the root is opened, with the drive type decided from the lexical drive prefix (`X:\`) before anything resolves the path. Those are observations of the path by name, not a guard against a concurrent ancestor replacement. A change marks the nearest indexed parent and its descendants stale, listed sizes are not refreshed, the ghost view is cleared and a notice records the count; kernel overflow or the 64-path cap marks the whole root stale with the change count and paths unknown. Stale cells keep the dashed border the ghost view also uses, and their tooltip says they changed since the scan and that Rescan refreshes them. A repeat that changes nothing is not recorded twice in a row; an overflow is always recorded. A watcher that ends without reporting an error turns the option off instead of leaving the box checked, and a worker that reports a failure or panics is reported in the console. Nothing is rescanned automatically. Stop and close turn the option off, and Stop records the stop when watching was on; Rescan retires the current watcher and, while the option is still on, a new one starts when the replacement scan finishes.

The notices panel is closed by default and keeps at most 256 session entries: directory failures with their Win32 codes, the scan's fallback and skip summary, watcher changes, rescan reasons, bookmark errors, ghost comparisons and snapshot errors. Each entry has a UTC time, a short text and the full detail on hover; Silence stops new entries and keeps the existing ones. Nothing is written to disk.

View → Add bookmark… saves the current location under a name of up to 128 characters, and View → Bookmarks lists the saved entries with Remove and Clear all. They live in `bookmarks.json` in the application-data directory, separate from the preference file, and store only the chosen name, root, native path components and optional member names as UTF-16 code units. Limits are 64 entries, 128 characters per name, 512 components, 256 members, 255 UTF-16 units per component, a reconstructed path below 32767 units and a 1 MiB file; a corrupt, oversized or future-version file is reported and left unchanged. Choosing a bookmark from another root starts a scan of that root and navigates when it finishes.

View → Rescan this folder (Ctrl+F5) requests the current location, but the append-only index cannot replace a subtree transactionally, so it always ends in a full rescan of the selected root or sample and states the reason in the status line and its tooltip.

### View modes, grouping and options

**View → Nested** (the default) and **View → Flat**, or Ctrl+Shift+V outside text fields, choose how many levels the map draws. Flat lays out one level below the drawn root and leaves deeper folders as whole rectangles, so opening a folder replaces the view; Nested draws the configured number of levels, one to 64 with three by default. The choice is not saved.

**View → Group by → None, Extension or Class** replaces the current folder's immediate items with synthetic groups: extension names such as `.jpg`, the first matching session class name, or `Other` for folders, extension-less files and extensions no class defines. A group keeps its members, so double-clicking it opens them, and its weight uses the same corrected totals; under Filter, a group with no retained file is not drawn. Grouping applies to the folder you are viewing, not inside an opened group, and editing classes rebuilds a grouped map. The choice is not saved.

**View → Options…** opens a modal with the minimum cell area (1–1,000,000 px²), the header height (0–64 px), the number of levels drawn below the current folder (1–64, default three) and whether small siblings are grouped. Values apply to the next layout and are rejected outside those ranges, keeping the previous ones; nothing is saved. Turning grouping off passes the smallest positive area instead of zero, because the layout rejects a non-positive minimum area and that value puts every sibling above the threshold. More/Less detail changes the drawn depth by one level and never touches the minimum area, so a custom area survives both actions; each action is disabled at its end of the range, and flat view keeps its single drawn level. A selected group is dropped when a class edit or a filter change could give its identity to another group.

**View → Show ghosts** keeps entries that disappeared between two scans of the same live root: after a finished rescan they appear as stale cells at their last listed sizes, matched by native relative path and, when both exist, by identity. A different identity at the same path is a replacement, not a ghost, and a partial or inaccessible parent produces none. The map then draws a derived index, so its totals are not comparable with volume capacity: the volume and estimate cells are omitted and the shell context menu is unavailable while ghosts are shown. The baseline is captured when a scan starts, so enable the option before the rescan it should compare. **View → Clear ghosts** returns to the live map and clears navigation and selection.

### Command line

The binary parses its arguments before creating a window. They are data, never commands: a path stays native, a filter expression uses the expression field's parser, nothing is shell-expanded, and nothing is executed.

```text
hogmap.exe [--scan <path> | --open <snapshot>] [--filter <expression>] [--metric logical|allocated] [--theme dark|light]
hogmap.exe --help
```

`--scan` starts the same background path/volume preparation as a chooser Start and then scans that directory. `--open` decodes a version-1 snapshot before the window exists and installs it as loaded, not live, data. `--filter` applies the expression and starts in Filter mode. `--metric` and `--theme` override the session metric and the stored theme. `--scan` and `--open` are mutually exclusive and each flag may be supplied once.

`--help` prints the usage and exits **0**. A bad argument, a missing or repeated flag, an invalid expression, metric or theme, a scan path that is not an existing directory, or a snapshot that cannot be read exits **2** with a message before any window is created. A failure returned by eframe itself exits **1**. Paths on the command line are visible to other processes; the usage line says so. The [command-line contract](https://github.com/Yivas/hogmap/blob/main/docs/core.md#command-line) lists the exact messages.

### Snapshots and text files

Use **File → Save snapshot… (Ctrl+S)** after scanning and hard-link checks stop. The native Windows dialog chooses a `.hogmap` file. A partial/cancelled scan keeps its incomplete metadata. **Open snapshot… (Ctrl+O)** also appears in the startup chooser. It restores the tree, tags, metric and historical volume observations without visiting stored paths. The file name and **not live** label stay in the header/status; navigation and filtering work, while shell actions and Rescan are disabled. Errors preserve the current view. Version 1 accepts at most 1,000,000 entries, 256 MiB of encoded names, 512 MiB per file and depth 512; these are snapshot limits, not scan limits. A larger scan cannot be saved. Unknown/newer versions, corrupt hierarchy, truncated input and trailing data are rejected rather than guessed.

**File → Export view as text… (Ctrl+E)** previews the first 20 lines and total line count before **Save text…** opens the native destination dialog. It captures the current zoom/member view, active expression/mode and metric, followed by tab-separated, indented drawn tree cells with exact bytes and parent percentages. It does not expand aggregates or list entries without area; unknowns remain marked in folder/group totals, never zero. Non-file volume cells are omitted. Cancel/Escape writes nothing. The [core contract](https://github.com/Yivas/hogmap/blob/main/docs/core.md#current-view-text-export-version-1) defines the fixed UTF-8/LF format, escaping and incomplete percentages; no templates, scripts or executable output are supported.

These shortcuts do not intercept typing in the expression field. Snapshots contain private names, paths, timestamps, identities and tags; exports contain visible names and the active expression. Neither stores analyzed file contents. Share only sanitized files. Opening is untrusted parsing, not authentication of a saved scan. Save/load use synchronous UI-thread I/O and can pause interaction on large or slow files. Automatic persistence remains geometry/theme only, apart from the explicit bookmark file described above.

Human-only checks: native Open/Save dialog ownership and focus at the existing DPI; cancellation and overwrite confirmation; preview scrolling and Escape; Ctrl+S/O/E while editing an expression must not open a dialog; save a small synthetic tree with a tag, reopen it, then navigate/filter it and confirm **not live**, historical capacity and disabled shell/Rescan. No native dialog was exercised by headless tests. Security review and native acceptance remain separate.

### Shell context menu

Right-click a real file or folder cell to select it and open Windows' **classic** shell context menu, the menu behind Windows 11's “Show more options”, not its compact modern menu. This also works in zoomed folders and on individual members of an opened group. Shift requests extended verbs. Windows and installed extensions supply the commands and execute only the one you choose, with their own configured confirmations. HogMap implements no delete, move, rename or clean operation, adds no free-space command, and invokes nothing automatically. Rename may be absent or fail without Explorer's editable ShellView/site; a failed verb displays its HRESULT rather than falling back to a HogMap implementation.

Aggregates, their subset-context header, the synthetic sample, drive-root headers and volume/estimate cells have no shell menu. Open a group to choose an individual file/folder. If a real item is missing, the status says **“This item no longer exists. Rescan to refresh.”** After a command, a detected disappearance or metadata change says **“The shell may have changed this item. Rescan to refresh.”** The full notice is available in the status tooltip and accessible label. The handler does not refresh the index automatically; use Rescan. Running scans continue their ordinary work, with bounded-channel backpressure while the UI thread is inside the modal menu.

HogMap constructs paths from native components and the captured absolute scan root, not display text, and checks metadata without reading contents or adding reparse resolution. Long paths are not truncated, but individual shell providers may reject them. The before/after comparison is best-effort, not identity proof; asynchronous changes or replacements with the same metadata signature can be missed. Installed extensions run inside the process and may have their own I/O/UI behavior, hang or crash it. There is no timeout or sandbox. Windows controls the menu's appearance and accessibility; it is not restyled to match egui.

Automated coverage separates pure native path tests, recorder-only headless selection/request tests (both themes and desktop widths), literal SDK ABI layout checks, and one small owned native file fixture (excluded from the default suite: run `cargo test --locked -- --ignored`; see the core contract). That fixture only parses/binds, obtains IContextMenu, calls QueryContextMenu and reads canonical command strings: it never displays/tracks a menu or invokes a command. The unsafe boundary uses the existing windows-sys 0.61.2 plus shell/COM/window features, not a new package; see the [technical contract](https://github.com/Yivas/hogmap/blob/main/docs/core.md#windows-shell-context-menu).

Human-only acceptance remains pending. With a disposable small local fixture and the existing display settings, check:

- File and folder right-click selection at the root and inside a zoomed folder; popup at the pointer in both themes and at the actual DPI (also another existing monitor, if available).
- Shift-right-click extended entries; mouse/keyboard dismissal must invoke nothing.
- Send to and Open with submenus, when Windows supplies them; check owner-drawn items and keyboard navigation with the installed providers.
- Properties and an Open-like command; report any HRESULT. Check Rename only if offered, recording unsupported behavior rather than treating it as verified.
- Windows Delete on a disposable fixture item only: confirm that Windows owns any configured confirmation, cancel first, and check the rescan notice if a later intentional operation changes the item. Do not change confirmation/security settings to force a dialog.
- An item removed externally after scanning: the exact missing-item message, no menu invocation and no automatic index change.

Do not use real data for destructive checks. A native dialog, DPI, submenu or screen-reader result cannot be inferred from headless tests. If antivirus/security software raises a prompt, stop rather than disabling it.

### Map legend

The window opens in the dark theme, or in the theme chosen last time. A saved light theme is applied before the first frame, so it does not flash dark. Both themes draw the same rectangles, headers and labels; only colors differ. Some states also have a mark that does not depend on color; the others are told apart by fill only.

- Brown (dark theme) or tan (light theme): directories, with a name/size header when space permits. Four deliberate levels get lighter in dark and darker in light; deeper levels reuse the fourth. Adjacent fill ratios are 1.197/1.199/1.208 in dark and 1.252/1.260/1.240 in light, above the design threshold 1.18:1 (not a WCAG boundary rule). Directory borders are darker than thin file seams. No map gradients, glows or shadows are added.
- Blue in **Flat Colors**: files with known bytes in the selected metric (logical by default, or allocated). **File Classes** uses the first matching class in name order instead; unmatched files stay blue. View selects either style and Ctrl+T switches them outside text fields, without changing geometry. Neither style nor class edits are saved. Partial/inaccessible and filter tones still take precedence.
- Small coloured plates with black numbers 1–4: effective tags, including inheritance. They reserve label space and remain identifiable without colour; a band shorter than 15 points or too narrow retains only the tooltip/accessible tag text.
- Green Free space: independently known volume capacity in either metric, only at an unzoomed whole-volume root. During scanning it is provisional capacity read at scan start; after Finished it needs eligible final NTFS origin/continuity observations. Unknown total alone does not erase known Free.
- Gray Not yet scanned · estimate: a positive running residual, not measured inaccessible bytes. Unknown required inputs or a non-positive residual leave no drawable estimate, with a reason; the gray cell disappears at the terminal.
- Reserved by Windows: known storage reserve with the existing allocated/Finished gates. These non-file cells support keyboard focus and accessible metadata names, not file selection, zoom or actions. Folder and zoomed views omit them.
- Lilac: small-item aggregates, with a dotted inner border when the cell is at least 24 px on each side. Each has a count/size label when it fits and a hover tooltip such as “12 small items · 1.2 MiB”; double-click opens those members. The tooltip names the metric, such as “12 small items · Apparent size: 1.2 MiB logical”. Inside that member view the root header keeps the parent folder's name and adds the subset, such as “photos · 12 small items - 1.2 MiB”.
- Gray with a dashed inner border: partial entries, such as a folder whose scan was cancelled before it finished.
- A dotted line under a header: the folder's total is incomplete, because some sizes are unknown or some content below it is partial or could not be read. Its size reads “+ unknown”. Unknown sizes are not zero and have no area of their own.
- Dimmed, near-background gray: non-matching entries while highlighting; olive (dark) or muted beige (light): an unknown filter decision.
- A thin outline follows the pointer and a thicker, stronger outline marks the selection; on cells smaller than 8 px both are drawn just outside the cell. Keyboard focus is a dashed ring with a solid backing, outside the cell.

Marks are skipped on cells smaller than 8 px on either side.

UI text uses a 13-point base, the status uses 12 points, and map labels use 11 points with monospace second-line sizes. Spacing follows 4/8-point steps. The desktop's header bands are 20/16/15 points, with separate horizontal/vertical insets so the measured text row fits. Names shorter than the readable three-character minimum stay in tooltips; final galleys that do not fit are omitted. Map labels keep a contrast ratio of at least 4.5:1 against their fill in both themes and both styles. Class palette fills (dark/light) and measured label ratios are: Blue #35597A/#9DC8E5, 6.574/11.827; Green #305C48/#A6D1B5, 6.840/12.409; Purple #60456E/#C8B4DB, 7.309/11.007; Amber #6A502A/#DBBF8C, 6.733/11.843; Rose #6C424B/#D9ADB8, 7.469/10.620. Dark class labels use #EEF3F8, light labels black. Tests also cover the existing interaction/state marks and seams on every class fill. A human still needs to check tag-number legibility, class-colour distinction, dialog keyboard/focus order and both styles in both themes at the actual DPI. That checks the palette, not full accessibility.

The total is labelled Apparent size: `known_bytes + resolution_delta_bytes` for the selected metric. The charged record uses the authoritative size; aliases retain listed sizes. There is no full per-name authoritative correction or error bound. Apparent size can exceed disk capacity; unique allocated bytes per identity instead determine the separate estimated difference. Cell sizes and areas use the same per-name apparent total: logical by default, or observed allocated bytes in the allocated view (`Index::summary_for`, `layout_with_metric`, `layout_members_with_metric`), with its own unknown sizes, missing identities and conflicts. Neither is physical or recoverable space. Filter `s`/bare size conditions compare listed logical bytes; `d` compares listed allocated bytes in either map view. The header displays queried global filesystem free/total capacity separately, or unknown if unavailable. Capacity uses the Actual fields of GetDiskSpaceInformationW (available from Windows 10 build 17763), never its caller-quota fields. The existing chooser/header hover and accessible details show the provider, query age and a reason when capacity is unknown; exact capture time and provenance are retained in memory, not saved. A local non-elevated Windows 11 metadata test exercises the real provider; quota-enabled/pool environments and atomic reconciliation with a scan are not verified. See the [capacity semantics](https://github.com/Yivas/hogmap/blob/main/docs/core.md#windows-metadata-engine). The map normalizes only displayed tree/volume/estimate values. In Logical view, logical tree bytes and volume-capacity bytes are comparable only in order of magnitude, not physical attribution. The status says the map is not a complete disk partition and reports estimated difference against corrected unique allocated bytes at both endpoints, or why it is unavailable. Status, tooltips and About show the repeated hard-link name total (`allocated_apparent - allocated_unique`) separately. The map counts each listed name, so map + free + reserve + estimated difference can exceed disk capacity by those repeated-name bytes. D <= 0 stays a signed discrepancy, not area; arithmetic overflow is reported. Difference has neither a cell nor an implicit blank area. Unknown components are omitted; reserve failure need not erase known free. No inaccessible-space block or alternate view mode is implemented. Headless geometry and accessibility checks are not native visual acceptance.

Only the window geometry and the chosen theme are saved automatically in eframe's application-data directory, together with the separate `bookmarks.json` that the bookmark actions write. That file holds the names, roots and path components the user chose and nothing else, so it is private data; filter text, classes, navigation and egui's own widget and window memory are still not saved. Explicit file saves are separate. A stored theme value that is missing, unknown or unreadable falls back to dark. AccessKit is enabled, but a full screen-reader and DPI acceptance pass is still pending. If eframe returns a startup error, HogMap prints it to stderr and exits with code 1; there is no native message box or automatic graphics-backend fallback.

## Headless release map benchmark

Use release builds for performance comparisons; a debug window is not a release timing baseline. The opt-in benchmark below streams the existing one-million-entry synthetic fixture in memory, without filesystem scanning or a native window. From the source root, in a temporary PowerShell process:

```powershell
pwsh -NoProfile -Command '$env:HOGMAP_BENCH_UI="1"; cargo run --release --locked --example scan_bench -- --synthetic-million --workers 1 --unthrottled-drain'
```

This mode requires the default desktop feature and rejects debug builds. It measures a 1920×1000 map, depth two, minimum cell area 400 and header height 20: cold layout, five warm layouts, label preparation, drawing, and layout after 64 small appends. It also measures initial empty/`*.bin;>32kb` highlight evaluation and five forced map rebuilds including layout, real highlight results/counts, prepared labels and drawing. Those forced rebuilds are not normal unchanged frames (which already reuse the UI cache); they exclude application chrome, input/event draining, native graphics and scan concurrency. Later stages add five warm reevaluations and a cached query for that filter, cold and warm filtered geometry for `*.bin;>32kb` and for a compound filter (`*.bin;\directory*;s>32kb;d<1gb;m<2w;-:attr:hidden`), and diagnostic timings for a folder mask, a class and a general wildcard. The separate draw microbenchmark uses unknown highlight decisions. Digests and counts accompany the timings; milliseconds are local observations, not performance guarantees. On 2026-11-15, reusing child lists, linear reverse-ID totals and skipping zero-weight name comparisons reduced first real/compound filtered geometry from 175.253/176.062 to 17.040/17.914 ms on this uncorrected 1M fixture with unchanged digests (real warm median 5.619→4.420 ms over five samples), but a separate synthetic corrected snapshot still needed 228.329 ms initially and 230.075 ms median over five forced layout rebuilds because original hardlink-charge ownership retains a forward hash pass; see the [measurement boundary](https://github.com/Yivas/hogmap/blob/main/docs/core.md#highlight-and-filter-consumers).

On one Windows x64 machine with Rust 1.94.1 release, 2026-11-10, layout changed from 432.218 to 248.025 ms cold, 421.047 to 7.453 ms warm median, and 407.969 to 7.973 ms after 64 appends, with identical geometry/member digests. Warm label preparation changed from 5.384 to 1.456 ms with the same fitted-label digest; only three labels fitted this particular 2001-cell viewport. Append work rose from 0.009 to 0.030 ms. Drawing did not show a consistent timing gain (1.012 versus 1.119 ms in the comparison), despite retaining scratch capacity.

A separate staged comparison, already using the optimized layout but before/after incremental highlight caching, changed forced rebuild medians from 28.286 to 10.002 ms with the empty filter and 184.504 to 9.920 ms with the real filter. Results stayed at 998999/0 and 491456/99 matching/unknown files respectively, with identical highlight digests. First real-filter evaluation remained expensive: 172.790 versus 163.950 ms; a new filter still evaluates the whole index. A query after the appends took 0.236 ms. Layout/filter cache capacities totalled 46276284 bytes (about 44.13 MiB), included in `IndexMemory::total_bytes()`; total index estimate was 280108748 bytes after growth. Peak process working set changed from 392249344 to 323092480 bytes, below 500 MiB for this synthetic headless workload only. These are single-process comparisons with five warm samples, not a frozen hardware study or native/DPI acceptance. These historical microbenchmarks predate the filter-engine rewrite and the current control/header/typography refinement; they are not full-renderer frame timings.

Headless UI checks cover both themes at 1914×1035 and 1280×720 logical points: toolbar names and absent tools, selected-path feedback, unclipped status text, four aligned chooser rows with independently known/unknown capacity, keyboard activation, and labels in reduced header bands. Egui's first auto-sized panel pass is provisional; these geometry assertions use settled passes. They cannot judge whether the interface looks right on a native display, or certify DPI and screen-reader behavior.

### Full renderer and ingestion measurements

Add process-local `HOGMAP_BENCH_LIVE_FRAME=1` alongside `HOGMAP_BENCH_UI=1` for the real desktop renderer (`Context::run_ui` plus tessellation), not a separate drawing model:

```powershell
pwsh -NoProfile -Command '$env:HOGMAP_BENCH_UI="1"; $env:HOGMAP_BENCH_LIVE_FRAME="1"; cargo run --release --locked --example scan_bench -- --synthetic-million --workers 1 --unthrottled-drain'
```

It forces stable, hover and growth frames at 1920×1000, then measures the million-entry stream with the real reducer and UI together. UI and tessellation time, shapes/vertices, drain-only distributions and rebuild counts are separate. An unchanged idle frame already requested no repaint in the baseline; forcing frames measures their cost, not an idle 30 Hz reduction.

A separate opt-in `HOGMAP_BENCH_EXTRA=1` with `--synthetic-million` measures complete/incomplete terminals and a 3.8M-entry memory fixture, without filesystem scanning. The private identity ledger is sharded, batches resume through a deadline-checked cursor, and layout storage grows amortized. These preserve existing accounting and ordering tests; they do not bound total scan memory. Native visual, screen-reader and DPI acceptance remain separate.

## Know the boundaries

- `src/index.rs` owns the flat metadata snapshot, entry IDs and per-metric listed/identity-accounting facts and the checked `MetricSummary::apparent_bytes()` area total. `known + delta = unique + shared` remains true; unique/shared are accounting facts, not geometry weights; corrected unique allocated bytes are the basis of the estimated difference.
- `src/filter.rs` owns the strict filter grammar, supplemental metadata, in-memory class/tag tables and cached Yes/No/Unknown decisions. Sizes can be logical or allocated; age references are fixed when applied. Windows batches carry existing listed timestamps/flags without extra file opens; ADS stays unknown. `Filter::matches` supplies snapshot-owned file decisions/counters and `FilterMatches::totals` separates matched/undecided apparent weights. Empty directories remain non-matching context. `layout_filtered` consumes the same decisions without reevaluating names. See the [filter reference](./filters.md) for precedence and unknown handling.
- `src/composition.rs` evaluates typed accounting eligibility without GUI dependencies. Known final free/reserve availability is independent of positive D. Fixed-answer tests distinguish apparent geometry from corrected unique-byte differences with hardlinks, hard gates, signed discrepancies, overflow, zero and unknowns; unreadable/unknown/skipped/fallback coverage remains diagnostic, without granting area to D. The desktop separately evaluates provisional Free and the running estimate. Headless UI tests cover proportional cells, both themes, visibility, keyboard/AccessKit behavior, cancellation and stale generations.
- `src/scan.rs` defines the generation-tagged scanner contract, bounded batches and the reducer that builds an index.
- `src/scan_win.rs` enumerates Windows directory metadata with bounded workers. The additive `run_win_scan_observed_with_options` returns outcome/report plus a generation-linked origin sidecar: scope, namespace observations and bound capacity endpoints, with typed unknowns/cancellation. Its origin queries use metadata-only directory handles; scheduling retains the legacy seek-penalty hint, worker policy and conditional NTFS MFT ordering. Queries run outside the shared observation mutex, with a reusable buffer per observed worker. It compares directory serial64 first and attempts GUID paths only on mismatch/unavailable identity; separate counters retain both kinds of evidence. Serial64 agreement is not GUID proof. Post-enumeration metadata queries run before the terminal and can delay it, including on a blocked network query; legacy mode is unaffected. Legacy scanner signatures and their Copy counts/timings-only report are unchanged and make no supplementary observation calls; the UI uses the observed path, retaining facts in RAM only. The root's filesystem name is captured in the same existing by-handle call as its support flags, without an extra query/open. The [origin contract](https://github.com/Yivas/hogmap/blob/main/docs/core.md#optional-origin-observations) explains opaque identities, alias ambiguity, lifetime and non-atomic endpoints; this is not reconciliation or gray eligibility. At that boundary an unsupported all-zero 128-bit file ID becomes unknown identity, not a shared hardlink; known logical/allocated sizes, including zero, are preserved and charged individually. Missing-identity counts are per metric and independent of size/state coverage. The primary path can lack identity while allocated size stays known; the fallback lacks both. `src/volume.rs` queries drive roots, labels, capacities, filesystem and whether the device reports a seek penalty. The scanner currently uses four workers on both SSD and HDD (the HDD value is provisional), and on NTFS hard disks it visits pending folders in MFT record order to reduce head movement. `examples/scan_bench.rs` measures a scan from the command line without printing paths or names; see CONTRIBUTING.
- `src/synthetic.rs` streams a separate deterministic in-memory tree through that contract.
- `src/treemap.rs` computes squarified rectangles, headers and navigable aggregates without drawing, weighted by logical or allocated bytes.
- `src/cli.rs` parses the startup arguments into a `Startup` value or an exit code with a message, without touching the filesystem, and validates that a scan path is an existing directory before the window is created.
- `src/ghosts.rs` derives a stale-entry view from two indexes of the same live root. It matches native relative paths and identities, creates nothing under a partial or inaccessible parent, and never mutates the live index; its totals are a presentation of absence, not volume accounting.
- `src/main.rs` and `src/ui/` own the desktop consumer, cached rendering, navigation and UI strings. `src/ui/options.rs` holds the session layout options: minimum cell area, header height, drawn depth and small-sibling grouping, with their validated ranges.
- `tests/core.rs`, `tests/scan.rs`, `tests/treemap.rs`, `tests/aggregate_navigation.rs` and `tests/navigation.rs` check public behavior and pure UI logic with fixed expected answers, including independent logical/allocated charges, conflicts, missing identities and per-metric overflow. Unit tests in `src/ui/` check location text, volume-choice mapping, path validation, scan-code messages, theme contrast and the stored theme preference. `tests/scan_win.rs` exercises small real Windows fixtures, not whole drives. A module-local aligned-buffer fixture feeds the actual Windows parser and index with equal-size zero-ID files, including known-zero sizes, and nonzero 128-bit hardlink IDs; this is simulated unsupported-provider metadata, not runtime reproduction on an installed filesystem. One native module-local regression constructs four small owned files (normal, compressed, sparse and an empty default stream with named-stream data), closes construction handles, then exercises the actual scanner/events/reducer/index path. It compares indexed allocation with the raw field from a separate native directory enumeration, independent of the scanner parser and reducer; this checks value transport, not physical attribution. It prints anonymous allocation observations, explicit capability omissions and cleanup confirmation; `allocation_verification_complete=1` follows those fidelity assertions and means all requested modes and primary enumeration ran with known allocation. A passing test with omissions does not certify those modes. The [local observations and stream limits](https://github.com/Yivas/hogmap/blob/main/docs/core.md#windows-metadata-engine) do not establish all-stream or physical totals.
- The [core contract](https://github.com/Yivas/hogmap/blob/main/docs/core.md) is the technical reference for implemented behavior.

For an owned synthetic tree of 20021 empty directories, five alternating warm runs per mode gave median observed overhead of 75.722% originally, 35.369% with per-directory GUID queries outside the mutex, and 0.203% with serial64-first queries. The preselected small-cost threshold was 5%, so serial64-first was retained. This is a local comparison with variable samples, not a general performance or UI promise; [timings, spread and evidence limits](https://github.com/Yivas/hogmap/blob/main/docs/core.md#observed-scan-cost) are recorded together. The headless example defaults to legacy; process-local `HOGMAP_BENCH_OBSERVED=1` selects observed scans and anonymous counters without changing benchmark guards. Observed diagnostics also include root scope/issues, capacity endpoints, relative wall-clock times, identity/path continuity and signed differences against allocated unique bytes, with explicit unknown reasons. They do not calculate eligibility or decide the treatment of unreadable directories; real-volume capacity and difference values are not published here.

Checked u32 entry-ID and name-arena ceilings return `CapacityExceeded`; these [representation limits](https://github.com/Yivas/hogmap/blob/main/docs/core.md#metadata-index) are not a safe process-memory budget, and allocation exhaustion can occur sooner.

Entry IDs belong to one index snapshot. The scanner contract checks the owning generation before applying records; the reducer never resolves an unknown parent later. IPC, privileged NTFS reading and physical attribution are not implemented. Small owned Windows fixtures now check the public scanner against an independent FindFirstFileExW walk for names, counts and logical sizes, and exercise create/delete changes with a publication gate. A discovered directory removed before opening keeps its real Win32 failure code and incomplete coverage; concurrent entries are not an atomic snapshot. A real path and a scan root longer than 260 UTF-16 units are enumerated from both ordinary and extended-prefix root arguments, using extended paths internally. The public observed API also scans that deep owned root: two directories, two files and 22 logical bytes, with a Folder origin, unchanged endpoints, known Actual* capacity and no fallback. A separate GetDiskFreeSpaceExW metadata probe succeeds on the same long extended directory with a trailing separator; its caller-quota free/total values are not assumed equal to global Actual* values. It is not the production capacity provider, which remains GetDiskSpaceInformationW with GUID-bound endpoints. A labelled synthetic stream through the real event channel and UI drain/render checks AccessKit status at initial/intermediate/Finished: 1/4/6 entries, 0/2/4 files and 0/11/16 known logical bytes. Finished still retains one unknown size and an intentionally unfinished directory as Partial; a known zero is not unknown. This is headless state evidence, not native progress, DPI or visual acceptance. These checks do not establish UNC or alternate registry/manifest configurations, desktop chooser acceptance, real cloud-provider behavior or safety against adversarial path replacement; see the [engine limits](https://github.com/Yivas/hogmap/blob/main/docs/core.md#windows-metadata-engine). The map uses a selectable minimum cell area (default 400 square points) and a drawn depth of 1–64 levels below the current folder (default three), which are independent controls; the depth is relative to the zoom rather than a fixed two-level stop. Snapshot-owned children/totals caches update along inserted or state-changed ancestor chains, with metric changes and authoritative corrections rebuilding as needed. During scanning, growth rebuilds wait at least 250 ms or four times the measured previous rebuild cost, whichever is longer, and are cached otherwise; the measured cost includes label and mesh preparation. Hover/selection reuse static meshes, theme/font/DPI/atlas changes refresh paint, and explicit metric/detail/navigation or resize changes rebuild immediately. Active ingestion uses roughly 67 ms logic ticks, not a 33 ms backlog repaint loop.

Read [CONTRIBUTING](https://github.com/Yivas/hogmap/blob/main/CONTRIBUTING.md) and open an issue to agree the scope before writing a pull request. Small documentation corrections need no prior issue.

A useful core bug report identifies the commit, Rust version and a synthetic reproduction. Do not include personal paths, machine names, credentials, disk listings or screenshots containing file names. Undisclosed vulnerabilities belong in the [private security channel](https://github.com/Yivas/hogmap/security/advisories/new), not in a public issue.
