# Understanding sizes

A size is useful only when its meaning is clear. HogMap keeps three different measurements separate. The Windows scanner supplies directory metadata to the current core, and the map uses apparent logical bytes per listed name unless View → Allocated size is chosen. The synthetic sample remains a separate in-memory fixture.

## Apparent size and geometry

The window's total is **Apparent size**, not used space: `apparent_total = known_bytes + resolution_delta_bytes` for the selected metric. Each listed name contributes. After conflict resolution, the charged record uses its authoritative size while aliases retain their listed sizes; unknown listed sizes stay unknown. This is not full per-name authoritative correction, and no error bound is claimed. Apparent size can exceed disk capacity. Unique allocated bytes per identity are reported separately and determine the estimated difference, not map area.

For listed hardlinks of 100 and 200 bytes plus an unrelated file of 50 bytes, correcting the charged 100-byte record to 300 gives apparent 550 bytes and unique 350 bytes. The alias still contributes its listed 200 bytes, not another corrected 300.

**Cell sizes and areas use that same apparent total in both views**, including the tree's proportions beside free/reserve cells. Subtree and aggregate totals include each of their known names. `MetricSummary::apparent_bytes()` checks the invariant `known + delta = unique + shared` as u64 and reports overflow; unique/shared retain their identity-accounting meanings and never decide area.

## Logical bytes

Logical size is the length of a file's data, not a promise about space that deleting it would recover. It is the metric used by the first filter implementation.

A zero-byte file has a known size of zero. A file whose size could not be obtained has an unknown size. Those cases must not be merged: an inaccessible directory or a failed read cannot be reported as empty.

The index summary reports visible logical bytes (`known_logical_bytes`), bytes charged once per file identity (`unique_logical_bytes`), bytes of later hardlink names (`shared_logical_bytes`) and the number of files with unknown logical sizes, all separately. Its completeness flag also reflects pending, partial, inaccessible and stale entries. Overflow returns an error rather than a plausible-looking capped total.

## Physical attribution

Allocated storage can differ from logical length because of compression, sparse regions, additional streams and filesystem allocation rules. Multiple hardlink names can also refer to the same physical file.

The index preserves optional allocated size and file identity, and the core now aggregates **observed allocated bytes** as a metric of its own, independently of logical bytes. In each metric a file identity is charged once, at its first entry with a known size for that metric, and later names add shared bytes. A known logical size does not consume the allocated charge, and an unknown logical size does not skip a known allocated size. `Some(0)` is a known size; `None` is unknown and is never treated as zero.

Neither metric is a deduplicated physical total, and **physical attribution is not implemented**. Two separate indicators expose risks to a reconciliation: entries with a known size but no identity, which are charged individually, and identities whose known samples disagree, which are counted once while the first charge is kept and no record is dropped. The primary Windows enumeration can provide allocated sizes even when identity is unknown. If the filesystem returns an all-zero 128-bit file ID because those IDs are unsupported, HogMap ignores it rather than treating unrelated files as shared hardlinks. Their records and sizes, including known zero, stay intact; each known size is charged individually and counted as missing identity in its metric. Size/state coverage and identity confidence remain independent. The fallback lacks both identity and allocated size, so fallback files are counted individually and allocated size stays unknown. The status tooltip and its accessible label report fallback directory counts after the engine returns.

An explicit backend post-pass can reread only identities with conflicting listed sizes, using one metadata-only file handle per selected identity and verifying its full file ID and volume before accepting FileStandardInfo sizes. The observed headless benchmark runs this after Finished. Real window scans run the same checks asynchronously, retaining the large index on the UI thread and discarding stale-generation results; legacy enumeration does not run a post-pass. The pass is capped at 4096 identities and cancellation-aware; denied, missing, unsafe, changed or unsupported observations leave conflicts with a reason. It does not read file contents or make an inaccessible directory readable.

Listed entry sizes, known/shared sums and unknown counts stay unchanged. Corrected unique charges have a signed `resolution_delta_bytes`, so `known + delta = unique + shared` remains true. Each metric is corrected independently only if it already had a charge and a known authoritative size; unknown listed charges are not filled. The treemap uses the correction at the entry that already owned the charge. A resolved index rejects new insertions; a rescan creates a new one. These later observations are not an atomic snapshot or physical attribution. See the [post-pass contract](https://github.com/Yivas/hogmap/blob/main/docs/core.md#explicit-conflict-reread).

The treemap can weigh either metric: `layout_with_metric` and `layout_members_with_metric` take the metric, and `layout`/`layout_members` keep the logical path. Each hardlink name gets its own known size and area. Only the first known record in the selected metric receives an authoritative correction; later aliases retain listed sizes, even when zoomed into their folder or aggregate. Every entry remains in the index, and an unknown size in the selected metric gets no area rather than being treated as zero.

In the window, View → Logical size / Allocated size chooses the metric. Logical is the default; the choice lasts for the session, survives a rescan and is not saved. The allocated view is labelled **observed**: it shows the allocation Windows reported per file, not physical attribution or space that deleting would recover. Files from the fallback enumeration have no allocated size, so they get no area in that view and the status counts them as unknown. The synthetic sample's allocated sizes are generated (logical sizes rounded up to 4 KiB), not observed. The status detail reports, for the selected metric, unknown sizes, known-size files without identity and conflicting identities separately; an overflow names its metric instead of showing zero. Highlight size conditions stay logical in both views. At an unzoomed whole-volume root, green Free space is independently available in either metric, provisionally while scanning and after eligible final observations. Reserved by Windows keeps its allocated/Finished gates. Folder and zoomed views omit volume cells. Gray Not yet scanned · estimate is a separate running residual, never an inaccessible-space block.

## Windows used and free space

Windows reports capacity and used/free space for a volume. A sum of file sizes is a different measurement. Filesystem metadata, shared allocation, access restrictions and a changing volume can explain differences.

The volume header shows global filesystem free/total capacity separately from map bytes. Windows GetDiskSpaceInformationW supplies Actual total/available allocation units, ignoring caller quotas; no caller-quota total or partition length is presented as filesystem capacity. Invalid units, arithmetic overflow, incoherence or a failed query leave both capacity values unknown with a reason, without erasing a known label or filesystem. A known zero-free value means a full volume, not unknown. The source and query-completion time stay in memory; chooser/header hover and accessible details show source, query age and any failure reason. This is an observation of a changing filesystem, not an atomic snapshot shared with the scan. Real quota-enabled and storage-pool environments remain unverified; see the [capacity contract](https://github.com/Yivas/hogmap/blob/main/docs/core.md#windows-metadata-engine). The map never reconciles logical totals with Windows used space. Its unzoomed whole-volume view can display independently known Free in either metric, and eligible allocated/Finished reserve; they are non-file cells with metadata tooltips and keyboard/AccessKit names, not folders or file actions. Unknown components are omitted with an explanation, not invented as zero.

The backend separately records Windows storage reserve and total reserved bytes from that same capacity query. Microsoft defines the per-volume storage reserve as **included in total reserved**; they are not two amounts to add together. Known zero stays zero. A failed base query leaves reserves unknown; a reserve-only conversion overflow has its own typed reason and does not erase valid total/free values. The meaning of the header's free/total values is unchanged. These fields are metadata observations, not an inferred partition of physical storage.

In the observed headless benchmark, the difference including reserve is `(total - free) - allocated_unique`. The difference excluding reserve is `(total - free - storage_reserve) - allocated_unique`, using reserve from the same endpoint sample. Both remain signed; unknown inputs keep an explicit reason rather than becoming zero. Total reserved is not subtracted again. These diagnostics do not establish eligibility or an atomic snapshot. The window uses final origin-bound storage reserve for its `Reserved by Windows` cell, independently of free. The window also calculates signed `D = total - free - storage_reserve - allocated_unique` at each endpoint. `allocated_unique` is the current identity-deduplicated allocated total after authoritative charge corrections; the correction is not added again. Its checked arithmetic reports overflow; D <= 0 is a discrepancy, never clamped or given area. This is separate from apparent map geometry. Status, tooltips and About show **Repeated hard-link names = allocated_apparent - allocated_unique** as its own number, or unavailable if it cannot be represented. The map counts each listed name, so map + free + reserve + estimated difference can exceed disk capacity by those repeated-name bytes. For two names of a 300-byte file and a separate 50-byte file, apparent is 650 and unique is 350; with capacity 1000, free 250 and reserve 100, D is 300, not 0. The apparent tree, free and reserve are normalized together, so there is no implicit blank area for D. **The map is not a complete disk partition:** estimated difference remains text only in the status and tooltips.

The backend also offers an optional observed-scan API that collects generation-linked root/volume scope, directory serial64 comparisons with GUID-fallback counts and origin-bound Actual* samples before/after enumeration. These are facts for later comparison, not a `comparable` flag or gray-space calculation. Root identities are opaque/redacted; failures, serial mismatches, ambiguous GUID names and omitted completion queries stay explicit. A matching serial64 is not a GUID proof; GUID fallback is attempted only for a mismatching or unavailable comparison. Endpoint agreement does not establish an atomic snapshot or physical attribution. The window consumes this sidecar in RAM; the header's preliminary drive query is never substituted for an authoritative endpoint. While running, a separately labelled provisional policy uses the fresh DriveChoice only when its local-drive root matches the lexically normalized scan root. It carries any valid known storage reserve from that same query, without adding a query or inventing identity evidence. A pure evaluator requires a proven whole-volume root, unzoomed Allocated view, Finished, known bound capacity/reserve at both endpoints, unchanged root identity/path, no allocated overflow, no unresolved identities or known allocated sizes without identity, no serial64 mismatch/different-GUID-unproven directories, and NTFS from the enumerated root handle. Either D <= 0 is a discrepancy, not area. Final Free has an independent visibility evaluation: a proven WholeVolume NTFS origin, unzoomed view, unchanged identity/path and a valid final capacity observation. It can be drawn in Logical or Allocated even when D is unavailable or nonpositive, including known Free with unknown total. Ineligible final evidence removes the provisional Free with a reason. Reserve retains its existing evaluator gates; reserve failure does not erase valid Free. Unreadable directories, unknown sizes, skips and fallback stay diagnostics, not measured causes of a residual. No inaccessible-space block is implemented; headless checks do not establish native visual acceptance. See the [origin-observation contract](https://github.com/Yivas/hogmap/blob/main/docs/core.md#optional-origin-observations).

## Running estimate, not inaccessible space

The gray **Not yet scanned · estimate** exists only during an active whole-volume scan. Its formula is `total - free - known storage reserve (if available) - displayed scanned apparent bytes`. For synthetic total 1000, free 200, reserve 100 and tree 300, it is 400. If reserve is unknown, the tooltip explicitly says it was omitted, not measured as zero; known zero remains known. Unknown total/free/tree prevents the estimate. A non-positive residual has no positive drawable estimate, not a measured zero or inaccessible amount. The gray cell disappears at the terminal.

The provisional tooltip says “Capacity read when the scan started; confirmed at the end”. Drive-root matching is not identity proof, and a changing scan is not an atomic snapshot. The final origin observation replaces this provisional basis. **Logical tree bytes and volume-capacity Free are comparable only in order of magnitude**, not physical attribution; per-name counts may exceed capacity. Only displayed values are normalized; no percentage or equality is forced. D remains the separate unique-allocated endpoint diagnostic, with no area.

## Folders with no known bytes

The window gives area to known logical bytes by default, or to known allocated bytes when that view is chosen. A folder with no known apparent bytes in the selected metric gets no rectangle. Known nonzero hardlink names do get area even if another name of that identity appears elsewhere. Its entries stay in the index, and any unknown sizes keep their unknown signal rather than becoming zero. Whether such a folder should keep a navigable empty cell is a product decision for the window and is not implemented.

## What is verified

The public API tests cover known versus unknown sizes, zero-byte files, logical and allocated hardlink charges, missing identities, conflicting samples, per-metric overflow and different logical/allocated geometry using synthetic metadata. Windows engine tests also scan small temporary fixtures with known lengths and hardlinks. An aligned-buffer parser fixture checks unsupported zero-ID metadata, known sizes and nonzero 128-bit hardlink accounting; it is not a runtime reproduction on an installed filesystem. A separate local native fixture runs the actual scanner through the reducer and index for normal, compressed and sparse files and an empty default stream with named-stream data. All four records kept their logical lengths and known allocation, including zero; the named stream did not increase the default-stream length. Independent handle/compressed-size observations and the exact local values are recorded in the [engine contract](https://github.com/Yivas/hogmap/blob/main/docs/core.md#windows-metadata-engine), not enforced as universal allocation constants. Unsupported fixture modes are reported explicitly; a portable test pass alone does not prove every mode was activated. These checks do not establish all-stream totals, whole-volume reconciliation, general compressed/sparse/ADS attribution or recoverable-space totals.

For the exact data model, read the [core contract](https://github.com/Yivas/hogmap/blob/main/docs/core.md). To see how logical sizes affect a query, continue with [filters](./filters.md).
